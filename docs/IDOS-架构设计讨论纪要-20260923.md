# IDOS 架构设计讨论纪要

> 日期：2026-09-23
> 性质：架构方向定稿讨论，含已落地的骨架代码说明

---

## 一、平台定位（定稿）

**IDOS = 数据中枢 + 模型支撑 + 插件宿主。**

- 平台**不做业务**：不建模、不分析、不调度模拟，业务全部由插件开发
- 第一版只支持少量数据，但**架构可扩展是最重要的事**
- 平台提供四样东西：组织方式（树）、显示方式（渲染）、协作方式（引用/信号）、接入方式（SPI）

---

## 二、术语澄清：`.DATA` 是什么

ECLIPSE 行业内 `.DATA` 文件被称为：

| 叫法 | 说明 |
|---|---|
| **Case（案例）** | 最常用 |
| Input Deck / Data Deck（输入卡） | 老派叫法 |
| Simulation Case（模拟案例） | 完整叫法 |

一个 `.DATA` = 一个完整模拟案例，通过 INCLUDE 串起所有子文件：

```
CASE.DATA
├─ GRID 段    INCLUDE → CASE.EGRID  (网格几何)
├─ PROPS 段   INCLUDE → CASE.INIT   (初始属性)
│             INCLUDE → CASE.UNRST  (重启属性，按时间步)
├─ SOLUTION  (初始压力/饱和度)
├─ SCHEDULE  (WELSPECS/COMPDAT/井控时间序列)
└─ SUMMARY   (输出请求)
```

**打开一个 `.DATA` = 打开一个工区/案例**，触发全链路 INCLUDE 递归 import。

## 三、平台四大块

| 块 | 职责 | 归属 |
|---|---|---|
| **输入树（INPUT 树）** | 多种数据导入 + 扩展，显示数据的层级结构 | 平台核心 |
| **模型树/案例树** | 案例创建（空案例）与打开（.DATA 引用链路自动挂载数据） | 平台核心 |
| **渲染窗口** | 平台必须具备的功能：各种数据的渲染 + 渲染设置 | 平台核心 |
| **插件** | 业务能力：模拟、拟合、分析；可拿数据、可挂载数据到案例、可写回结果 | 插件 |

---

## 四、两棵树的职责划分（重构核心）

**输入树 = 数据本体世界**

- 所有导入的原始数据（井/网格/属性等），可独立存在，不挂案例也能浏览、渲染
- 层级由数据自身结构决定（聚合根 → 子对象，树模型按 `containerId` 分流）

**案例树 = 引用世界**

- 案例 = 工况配置 + 引用集合
- 创建空案例 → 从输入树拖拽数据挂载（或插件挂载）
- 打开 .DATA → Coordinator 递归 import 全链路 → 自动挂载引用
- 数据本体永远只有一份；案例删除不动数据，数据删除先断案例引用

**渲染窗口 = 两个世界共同的视口**

- 渲染输入树对象或案例整体都行
- 可见性由 `IDOSDataObject::setVisible` 驱动，图层面板只是批量开关视图

## 五、渲染窗口设计（定稿）

```
渲染窗口（平台内部）
├── 数据获取：拿 objectId → project->objectById(id) → IDOSDataObject*
├── 映射表：objectId ↔ 渲染对象（vtkActor/vtkProp），渲染生命周期跟着 id 走
├── 类型分派：渲染器只声明自己认识的 typeId，不认识的数据直接不画
│            （新数据没渲染器就只在树里，不在 3D 里）
└── 内部功能：视口颜色、相机、灯光、交互……操作接口 v1 不对外
```

**"不开放"的确切含义**：渲染器的**功能操作 API**（改视口颜色、设相机等）不对外暴露。外部想影响画面，唯一途径是操作数据对象本身。

### 数据驱动的渲染生命周期

| 数据侧钩子 | 渲染窗口的动作 |
|---|---|
| `objectId` | 映射表的键：actor 创建/查找/销毁都按 id 走 |
| `typeId()` | 分派依据：找支持该类型的渲染器，没有则忽略 |
| `visibilityChanged` | 按 id 查映射 → actor 显隐 |
| `dataChanged` | 按 id 查映射 → 重建/刷新 actor |
| Project `objectAdded` | 可见且类型支持 → 自动建 actor 进场景 |
| Project `objectRemoved` | 按 id 查映射 → 删 actor |

## 六、插件的数据契约

```
插件启动 → 平台注入上下文（IDOSContext）
  ├── 读：project->objectById/objectByName 拿任意数据
  ├── 案例视图：model->refsByType(...) 拿本案例挂载的引用集
  ├── 挂载：model->addObjectRef(id) 把输入树数据组进案例
  ├── 计算：模拟/拟合/分析（插件自己的业务）
  └── 写回：结果 new 成 IDOSDataObject 子类 → project->addObject()
            （结果对象可再挂回案例，被其他插件继续用）
```

插件之间通过 Project 里的数据对象传递成果——模拟插件的输出可以是分析插件的输入。

## 七、引用模型设计（定稿）

**引用只存 objectId，不需要 role。**

- id 本身不带类型，天然类型无关
- "引用是什么角色"由被引用对象的 `typeId()` 决定，便利查询做类型过滤即可
- role 只有在"同类型对象在案例里有不同语义"（如双网格）时才需要，留待将来

```cpp
// IDOSModel 核心接口
void addObjectRef(const QString& objectId);       // 挂载任意对象
bool removeObjectRef(const QString& objectId);    // 断引用（本体不动）
const QStringList& objectRefs() const;            // 唯一存储
QString refByType(const QString& typeId) const;   // 过滤视图
QStringList refsByType(const QString& typeId) const;
```

- **存储只有一份 `m_objectRefs`**，新数据类型挂案例 = `addObjectRef(id)`，IDOSModel 永远不用改
- 便利函数靠 `project()` 查每个引用的 typeId（对象已感知所属工程）

## 八、引用的展示方式（定稿）

**核心：两棵树是同一个 Project 的两种视图组织，数据永远只有一份。**

```
输入树：  本体列表 ──→ 对象 ──→ 子结构          （根 = 本体）
案例树：  案例 ──→ 引用 ──→ 对象 ──→ 子结构     （根 = 案例，中转一层引用）
```

- 引用节点以下的整棵子树，和输入树里那棵**一模一样**（同一套子节点规则）
- 引用节点带角标/链接图标区分；可镜像展开本体的子结构
- 子树展开规则只写一份：`typeId → 子节点规则` 放类型注册表，两个树模型共用

### 两棵树的操作语义

| 操作 | 输入树（本体） | 案例树（引用） |
|---|---|---|
| 删除 | 删本体，先检查引用（"被 N 个案例引用，确认？"） | 只断引用，本体不动 |
| 可见性勾选 | 改本体 visible | 也是改本体 visible（两树天然一致） |
| 拖拽 | 拖拽源（mime 带 objectId） | 放置目标 → addObjectRef(id) |
| 右键菜单 | 本体操作（重命名/导出/删除） | 引用操作（断开/定位到输入树） |

## 九、通用性分析（定稿）

**判据：第三方不改平台代码，能否把全新数据类型/格式/业务全链路接入。**

| 全链路环节 | 机制 | 状态 |
|---|---|---|
| 新数据类型 | `IDOSDataObject` 子类 + `typeId()` 注册 | 对外开放 |
| 新文件格式 | Provider SPI + Metadata 注册 | 对外开放 |
| 进工程 | Coordinator find-or-create + mergeFrom | 对外开放 |
| 挂进案例 | 通用引用集（裸 id） | 对外开放 |
| 可视化 | 渲染器按 typeId 注册（平台内置演进） | v1 不开放，注册制实现 |
| 业务处理 | 插件读 Project / 案例引用集 | 对外开放 |
| 成果被下游复用 | 结果写回 Project 成新对象 | 对外开放 |

**与行业平台同构**：Petrel（工区+树+3D窗口+Ocean 插件）、ResInsight、OSDU 共同验证过的"数据中枢 + 插件宿主"模式。

### 通用性成立的三个前提（v1 必须做对）

1. **案例引用集泛化** —— 裸 id 列表，任何 typeId 可挂（已落地）
2. **树展示规则注册制** —— `typeId → 图标/子节点规则/右键菜单`，树代码禁止 if-else 具体类型
3. **序列化 typeId 工厂制** —— `.idos` 按注册的类型工厂反序列化，覆盖插件子类

共同纪律：**按 typeId 分发，绝不写具体类型 if-else**。

### 边界澄清

通用架构平台 ≠ 全能平台。出厂"什么都没有"（只有树+渲染窗口+几个内置数据）是对的。功能密度靠时间+插件+数据类型累积，架构不需要再动。

## 十、二次开发友好的五个机制（定稿）

核心理念：**开发者只声明"是什么"，框架负责"怎么接"**——所有接线工作（进树、序列化、挂案例、渲染、加菜单）收编到框架。

| 机制 | 内容 | 效果 |
|---|---|---|
| 1. 类型描述符 | 一个描述符统一声明序列化工厂/树规则/渲染器/合并语义，各有默认 | 学一个概念，四个子系统自动生效 |
| 2. 属性自描述序列化 | 子类用 Q_PROPERTY 声明字段，框架按元信息自动 save/load；大数据块走二进制段 | 新类型零序列化代码 |
| 3. Provider 极简契约 | 一个 `read(路径) → 对象列表` + 一行注册 | 导入后进树/合并/挂案例全自动 |
| 4. 插件最小契约 | `id() + initialize(context)`；context 一站式提供 project()/registerAction()/registerPanel()/currentCase() | 一行加菜单、一行加面板 |
| 5. 通用渲染路径 | 数据对象可选实现标准几何接口（点/单元/标量场），平台通用渲染器直接画 | 80% 类型零 VTK 代码 |

### 二次开发体验分档

| 想做什么 | 要写的 | 不碰的 |
|---|---|---|
| 新数据类型进树/存盘/挂案例/看属性 | 一个数据类 + 一份描述符 | 树模型、序列化、案例、GUI |
| 再加文件导入 | + 一个 Provider | Coordinator、合并逻辑 |
| 再加 3D 显示 | + 标准几何接口几个 getter | VTK、渲染窗口、信号接线 |
| 再加业务 | + 一个插件类 | Ribbon、Dock、菜单、事件 |

## 十一、v1 范围与演进路线（定稿）

### v1 范围

| 模块 | 范围 |
|---|---|
| 打开案例 | 选 `.DATA` → 创建 IDOSModel 案例 → Coordinator 走 INCLUDE 链路递归 import → 自动挂载引用 |
| 数据导入（独立） | LAS / Wellheader / .dev / .prn / .EGRID 单独导入，被案例引用或单独查看 |
| 工程管理 | `.idos` 工程装多个 case + 多个数据对象；案例只持 objectId 弱引用 |
| 树视图 | 输入树 + 案例树（同一 Project 两种组织） |
| 渲染窗口 | 渲染框架平台内置；v1 内置网格渲染器 + 井轨迹渲染器，注册制 |
| 插件宿主 | IDOSPlugin 接口 + 静态注册（编译期），4 类贡献点（菜单/面板/渲染器/算法） |
| 不做 | case 文本编辑（v2）；.INIT/.UNRST 属性场（v1.5）；分析算法（第三方插件） |

### 演进路线

- **v1**：井 4 类 + `.EGRID` + `.idos` + 两棵树 + 渲染窗口框架 + 插件宿主
- **v1.x**：每种新数据（生产数据 → PVT → 岩心 → 构造面…）走一遍标准接入流程
- **每一步 core/providers 已有代码零改动，只有新增**

### 新数据接入标准流程（八步）

| 步骤 | 谁做 | 内容 |
|---|---|---|
| 1. 领域对象 | 数据作者 | IDOSDataObject 子类 + 新 typeId |
| 2. 格式解析 | 数据作者 | Provider 子类 + Metadata 注册 |
| 3. 合并语义 | 数据作者 | override mergeFrom() |
| 4. 输入树展示 | **平台自动** | 树模型按 typeId → 展示规则注册 |
| 5. 案例挂载 | **平台自动** | 通用引用集，新类型直接可挂 |
| 6. 渲染器 | 数据作者（可选） | 按 typeId 注册；不注册则不进 3D |
| 7. 序列化 | **平台自动** | .idos 按 typeId 工厂反序列化 |
| 8. 插件读写 | 任何插件 | project->objectById() 拿到即用 |

### v1 验收标准

**"生产数据"作为一个全新数据类型，由插件全链路接入（导入→输入树→挂案例→渲染→被分析插件读取），全程不改 core/providers 已有代码。**
